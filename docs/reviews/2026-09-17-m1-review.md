## 1. [P1] registry 손상을 새 설치로 취급해 삭제 identity를 부활시킨다

코드: [registry.go:35](../../internal/store/registry.go#L35),
[server.go:78](../../internal/controller/server.go#L78).

`LoadRegistry`는 없는 파일을 빈 registry로 읽는다. 빈 파일과 YAML `null`도
정상 파싱되어 빈 값이 된다. `NewServer`는 기존 상태와 최초 설치를 구분하지 않는다.
따라서 lease와 영구 삭제 기록 `RemovedNodes`가 함께 없어지고 시작이 성공한다.

실제 mTLS 재현 순서:

1. node 발급/등록 → node removal → 옛 인증서 접근 거절 확인.
2. registry만 삭제, 0바이트, `null`로 각각 변경.
3. 동일 data_dir/PKI로 재시작. 세 조건 모두 성공.
4. 관리 token으로 같은 identity 재가입.
5. 옛 인증서의 public key 변경 등록이 다시 성공.

이 부활에는 손상 이후 재가입이 필요하다. 삭제된 파일만으로 곧바로 모든 API가
열리는 것은 아니다. certificate fingerprint revoke가 아니라 node removal로
차단했던 옛 인증서가 대상이다. 또한 `wg_apply` 시작 경로가 빈 registry를 적용하면
기존 WG peer를 제거할 수 있다. 후자는 코드 경로 확인이며 이번에 커널에서 재현하지 않았다.

조치: 초기화/버전 표식, 필수 구조 검증, 기존 상태 손상 시 fail closed,
복원·legacy migration·정상 0노드 상태의 구분. WG reconcile 전에 거부해야 한다.

[상세 이슈 초안 및 완료 기준](2026-09-17-m1-issues/registry-loss.md)

## 2. [P1] node serve 초기 등록 실패가 인증서 자동 갱신도 중단시킨다

코드: [main.go:654](../../cmd/vpnctl/main.go#L654),
[agent.go:25](../../internal/agent/agent.go#L25).

`node serve`가 `syncConfigOnce`에 성공해야 `agent.Run`이 시작되고, 인증서
maintenance는 그 안에 있다. registry/WG 명령 오류로 등록만 실패하는 동안에도
PKI API에 접근할 수 있지만 갱신 루프가 실행되지 않는다. 유효 인증서가 만료되면
등록 장애가 해소되어도 자동 재진입이 어려워진다.

재현은 production CLI subprocess + 실제 TLS, client 수명 6초 / 갱신 window
4초, 등록 503 / 사용 가능한 PKI endpoint 조건이다. 세 번 모두 등록 53–54회 동안
trust/renew 호출은 각각 0회였고 인증서가 만료됐다. ip/wg는 임시 PATH shim이며
호스트 네트워크는 변경하지 않았다. 전체 네트워크가 수명보다 오래 단절되어
재가입이 필요한 문서상의 한계와 다른 문제다.

조치: cached VPN 경로 복원을 보존하면서 supervisor의 재시도/backoff 전체 기간에
PKI maintenance를 유지한다. 중복 renewer, 종료 join, config 변경/CAS 경합도 검증한다.

[상세 이슈 초안 및 완료 기준](2026-09-17-m1-issues/renewal-supervisor.md)

## 3. [P1] silent direct peer sweep이 heartbeat와 health를 막는다

코드: [agent.go:132](../../internal/agent/agent.go#L132),
[agent.go:171](../../internal/agent/agent.go#L171).

direct peer를 하나씩 최대 2초 기다리고 결과 보고까지 동기 실행한다. 그 select
루프가 heartbeat, candidates 갱신, hub health도 소유한다. peer 여러 개가
응답하지 않으면 장애 판단을 맡은 제어 루프 자체가 오래 정지한다.

실제 agent.Run과 loopback HTTP/UDP, silent peer 3개로 1초 heartbeat가
sweep 시작 후 3초 동안 한 번도 실행되지 않음을 3회 확인했다. 32노드에서
나머지 31개 peer가 모두 timeout이면 probe만 약 62초이며 API 지연은 별도다.
62초는 코드에서 도출한 값으로 이번 32노드 실측값은 아니다.

#37/#40은 STUN 종료 교착 및 취소를 수정했지만 이 순차 sweep 경로는 남았다.
조치: bounded worker/sweep budget과 결과 제출의 backpressure를 정의하고
heartbeat/health 진행을 보장한다. 동시 WG apply와 stale generation 문제를
만들지 않도록 #20/#23과 연결한다.

[상세 이슈 초안 및 완료 기준](2026-09-17-m1-issues/direct-starvation.md)

## 4. [P1] registry/token의 성공 반환이 디렉터리 내구성을 보장하지 않는다

코드: [registry.go:93](../../internal/store/registry.go#L93),
[bootstrap.go:283](../../internal/pki/bootstrap.go#L283).
node config 저장에도 같은 패턴이 있다.

임시 파일 fsync 후 rename하고 끝나며 부모 디렉터리를 fsync하지 않는다.
`TestSaveRegistry_RoundTrip`과 `TestTokenExpiryLegacyMigrationAndFailedAdmission`을
시스템 호출 추적으로 실행해 이 순서를 확인했다. 두 테스트 자체는 PASS다.
반면 authority/credentials의 `pki.WriteAtomic`에는 부모 fsync가 있다.

이 누락 때문에 전원 장애 후 성공한 삭제/lease 변경 또는 token 폐기·단일 사용
소비 기록의 내구성을 보장할 수 없다. 실제 전원 장애와 데이터 부활을 실측한 것은
아니다. SIGKILL 테스트 통과는 이 항목을 대체하지 않는다.

조치: 부모 fsync를 추가하는 것과 함께, rename 성공 후 fsync 실패의 불확실한
커밋을 처리한다. 오류를 단순 반환해서 옛 메모리/WG로 rollback하면 디스크의
새 registry와 어긋날 수 있으므로 재조회·복구 계약이 함께 필요하다.

[상세 이슈 초안 및 완료 기준](2026-09-17-m1-issues/durability.md)

## 5. [P2] 인증서 발급 실패가 online 유령 노드와 CA gate 차단을 남긴다

[authority.go:606](../../internal/pki/authority.go#L606).

bootstrap은 registry 커밋 후 authority에 발급 결과를 저장한다. 뒤 단계가
실패해도 registry를 되돌리거나 미완료 등록으로 표시하지 않는다.

authority 파일 교체 실패만 주입해 token/registry 저장이 정상인 상태로 HTTPS

조치 대상은 enrollment의 reserved/pending/issued/active 경계와 재시도·정리이며,
실제 기존 노드를 CA gate에서 무조건 제외하는 방식으로 해결해서는 안 된다.

## 기존 테스트가 놓친 범위

- PKI 커널 matrix의 1/3/8/32노드는 `direct_mode=off`,
  `health_check_interval_sec=3600`이다. [구성 위치](../../tests/integration/pki_network_test.go#L175).
  인증서 전환·relay 경유 uplink 검증으로는 유효하지만 default auto/direct나
  실행 중 health 기반 자가 복구의 규모별 검증으로 확대할 수 없다.
- 별도 direct netns 테스트는 2노드 정상 상태에서 peer/endpoint 주입을 확인한다.
  direct 패킷 실패→relay fallback, silent fleet, 다중 relay handoff의 보장이 아니다.
- registry pre-rename 실패·프로세스 kill 검증과 directory metadata의 전원 장애
  내구성 검증은 다르다.
- 정상 동작 중 짧은 인증서 수명 검증은 supervisor가 agent 진입 전에 재시도하는
  동안의 갱신을 검사하지 않았다.
- API 인증 시 자신의 identity로만 변경하는 검증과, 삭제 기록 자체가 유실되는
  복원 경계 검증은 별개다.
- registry 저장 실패 bootstrap 테스트는 있지만 registry 성공 뒤 authority 저장
  실패의 부분 커밋은 검사하지 않았다.

다음은 신규로 수정 완료했다고 볼 수 없고 기존 이슈를 유지해야 한다.

| 축 | 아직 필요한 기능/검증 | 기존 이슈 |
| --- | --- | --- |
| M2 | quality snapshot 동시성, window/freshness 일관성, 중앙 history와 실제 품질, target server까지 단계별 uplink 상태 | #14–#19 |
| M3 | 실패 direct readiness 무효화, 실제 WG 경로 검증, 다중 relay/underlay, reconcile/rollback/anti-flap, fault matrix | #20–#25 |
| M4 | 관측→예측 입력, predictor runtime/API/fallback, 실제 trace replay, 로봇 프로세스의 target uplink 상태 API | #26–#30 |

특히 #14의 monitor snapshot data race와 #20의 실패 후 direct readiness 잔존은
현재 소스에도 남아 있다. 기존 전체 race 테스트 PASS가 해당 경로까지 검사한다는
뜻은 아니다. 다중 relay/underlay 전환이나 실제 LTE 장비 검증은 이번 M1 결과에
포함되지 않는다. VPN은 로봇의 서버 uplink 경로이며 로봇 동작 명령 기능이 아니다.

관리 token을 통한 동일 identity 재가입은 현재 문서가 명시한 key 복구 절차다.
이를 일반 인증 노드의 identity 위조와 혼동해 신규 취약점으로 판정하지 않았다.
다만 token은 임의 identity 재가입을 허용하는 높은 권한이라는 운영 전제가 필요하다.

  이번 리뷰에서는 동일 kernel matrix를 다시 실행하지 않았다. 새 발견 경로를
